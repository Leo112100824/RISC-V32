# 测试运行与故障排查

## 首次准备

需要 Python 3.10+、GNU Make、QuestaSim 2024.1（本工程已验证版本）及可用许可证。其他 ModelSim/Questa 版本尚未在本工程验证。把仿真器的 win64 目录加入 PATH，使 vlib、vlog、vsim 可调用。

在克隆后的仓库目录（含 README.md、rtl、model_tb 的目录）打开 PowerShell。先检查工具：

~~~powershell
python --version
make --version
where.exe vlib
where.exe vlog
where.exe vsim
make -C model_tb doctor
~~~

doctor 只做基本工具可见性提示，不能证明许可证或仿真成功。若 Python 命令名是 python3 或 py，可传入 PYTHON=python3 或 PYTHON=py。工具未加入 PATH 时，可在 Make 命令中传入路径（以下路径要替换为本机安装位置）：

~~~powershell
make regression-check PYTHON="C:/Python/python.exe" VLIB="H:/questasim/win64/vlib.exe" VLOG="H:/questasim/win64/vlog.exe" VSIM="H:/questasim/win64/vsim.exe"
~~~

本机已有的仿真器路径是 H:/questasim/win64/；换电脑后路径可能不同。GNU Make 对带空格的 Python 可执行文件路径可能需要额外引用，建议先将 Python 目录加入 PATH，或直接运行下面的 Python 命令。

## 没有 Make 时直接运行

以下均从克隆的仓库目录执行；如果工具已在 PATH，省略 --vlib/--vlog/--vsim 参数即可：

~~~powershell
python scripts/run_regression.py --suite all
python scripts/run_regression.py --suite unit
python scripts/run_regression.py --suite system
python scripts/run_regression.py --bench tb_alu
python scripts/run_regression.py --bench tb_top_module
python scripts/run_regression.py --suite all --timeout 120 --vlib H:/questasim/win64/vlib.exe --vlog H:/questasim/win64/vlog.exe --vsim H:/questasim/win64/vsim.exe
~~~

--timeout 是每个外部工具进程的墙钟秒数，默认为 60，不是 HDL 的仿真时长。

## 常用命令

| 命令 | 用途 |
|---|---|
| make unit | 跑 16 个模块的独立测试 |
| make unit-alu | 只跑 ALU；模块名用小写和连字符，如 make unit-if2-stage、make unit-rv32-core |
| make unit-top-module | 单独跑顶层端到端测试 |
| make sim | 跑原始指令级程序，检查 89 个结果和 8 个 trap |
| make regression-check | 跑全部模块测试，再跑指令级整核程序 |
| make test-runner | 检查回归脚本的失败、假 PASS 和超时处理 |
| make program | 重新生成整核测试镜像及期望文件 |
| make gui | 打开 QuestaSim GUI 和波形配置 |
| make clean | 清理 QuestaSim 工作库和常见波形产物 |

根目录和 RISC-V32/ 目录都提供了 Make 包装入口。回归失败时 Make 会返回非零退出码，可用于 CI 或脚本判断。

GitHub 克隆得到的是 RISC-V32 仓库自身，直接在该目录运行即可，不需要再进入一个同名子目录。日常调试先跑单测，修改完成后跑完整回归。命令行回归需要的 vlib/vlog/vsim 全部要可用；不用安装 RISC-V GCC、Spike 或 UVM。

## 查看结果

统一运行器位于 scripts/run_regression.py。每个 bench 的日志保存在 model_tb/results/，summary.json 汇总 PASS/FAIL、耗时和检查数。这些文件被 .gitignore 排除，不需要提交。原指令级 bench 的成功标志是 tb_top completed with no errors；每个单元 bench 会输出自己的 PASS tb_<name>。

先查看失败对应的 tb_<name>.log，搜索 Fatal、Error、FAIL。compile.log 保存编译阶段输出；summary.json 中的 reason 说明回归器检测到的失败类型。若报告提示工具不可用，先检查 PATH，或按首次准备章节显式指定工具路径。若提示超时，先在失败日志中看停滞位置，再用单项命令重跑定位。

~~~powershell
Get-Content model_tb/results/summary.json
Get-Content model_tb/results/tb_alu.log -Tail 60
Select-String -Path model_tb/results/tb_top.log -Pattern 'FAIL|Fatal|Error'
$LASTEXITCODE  # 应紧接在 make/python 回归命令后查看；0 为成功
~~~

summary.json 每次运行会被覆盖；目录中其他 bench 的旧日志不会自动清空，不能凭旧日志存在就认定本次执行过。编译失败先看 compile.log；许可证不可用、工具启动失败或超时也不是 RTL 测试通过。

## 打开 GUI 看波形

~~~powershell
make gui
~~~

当前 start.do 只自动运行 8000 ns，而原有 tb_top 要运行约 30016 ns 才完成。GUI 中继续输入 run -all 等待结果；不要把暂停在 8000 ns 当作通过。需要观察信号时，在 Questa Transcript 输入：

~~~tcl
add wave -r sim:/tb_top/dut/*
restart -f
run -all
~~~

GUI 针对独立模块时，先运行该单测编译，再从 model_tb 目录执行 vsim work.tb_alu（或对应 bench）。其余 bench 的时钟/复位和激励在各自 SV 文件内，不用手动驱动。

## 失败时的基本步骤

1. 用单项入口重跑失败模块，例如 make unit-if2-stage。
2. 检查该 bench 的期望值、输入激励和波形/日志；更改 RTL 后重跑单项测试。
3. 定向测试通过后运行 make regression-check，确认没有破坏其他模块或整核行为。
4. 如果更改了 model_tb/program/gen_test.py，先 make program，再运行 make sim 或完整回归。

完整 testbench 与覆盖内容见[单元测试说明](../model_tb/unit/README.md)；测试程序镜像的修改规则见[测试数据修改指南](测试数据修改指南.md)。
