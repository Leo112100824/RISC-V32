# 测试数据修改指南

本工程有两类测试数据：整核指令程序由 Python 生成器维护；独立模块测试的输入和期望值写在对应的 SystemVerilog bench 中。修改源文件后再运行测试，生成文件不要手工维护。

## 修改整核 RV32I/Zicsr 程序

主要编辑 model_tb/program/gen_test.py。文件底部按模块顺序构造测试程序；Asm 提供常用指令编码方法，如 i、r、load、store、branch、jal、csr、ecall、ebreak、mret。

建议第一次先加一个不会影响已有用例的算术测试：在文件的 “Trap summary / final checks” 段开始处、a.check("TRAP_COUNT", ...) 之前插入下面三行。此时异常用例已结束，下面只检查 trap 汇总，修改 x3/x4 不会改变其余检查：

~~~python
a.i("addi", 3, 0, 20)       # x3 = 20
a.i("addi", 4, 3, -7)       # x4 = 13
a.check("ADDI_NEGATIVE", 13, 4)
~~~

a.check(name, expected, reg) 会把被测寄存器写入结果数组，并按调用顺序记录期望值。新测试通过 checks.txt 的索引显示在仿真输出中。期望值是无符号 32 位比较，负数可直接写 -1 等 Python 整数，生成器会转换为 32 位补码。

当前 handler 为 mepc += 4 后执行 MRET，因此只会跳过一条 4 字节异常指令。新增 trap 时，要安排好返回指令并按实际事件顺序调用 a.expect_trap(cause)。此外必须修改 model_tb/tb_top.v 中固定索引的 mtval 检查，以及 MCAUSE_LAST 等依赖最终异常的期望值；不能认为 defs.vh 更新数量就完成全部接入。第一次练习建议只追加上面的普通算术检查，异常顺序保持不变。

生成和验证：

~~~powershell
make program
make sim
# 或运行包括所有模块的完整回归
make regression-check
~~~

make program 会同步重写 program.hex、expected.hex、trap_expected.hex、defs.vh 和 checks.txt。检查 git diff -- model_tb/program，确认镜像变化符合预期；生成文件需要和生成器一起提交，保证其他电脑拿到一致数据。

当前结果占 dmem 0x0000–0x0163，共 89 字；数据区从 0x400 开始，trap 日志从 0x600 开始。结果不能增长到覆盖数据区：保持现有布局时最多 256 个结果字。生成器只检查 store 的立即数范围，不自动检查区域重叠；imem 容量 1024 字，dmem 容量 512 字。指令和数据是两个独立数组，同数值地址不冲突。

保留 x1（结果基址）、x2（访存基址）及 x27–x31（handler 使用）的约定。每个新用例初始化自己读取的寄存器，不要依赖上个用例偶然留下的值。a.i 的普通立即数在 -2048..2047 内；更大的 32 位常量用 a.li(rd, value)。a.check 默认读 x5，若结果在 x4 必须像示例一样传第三个参数 4。

新增上述三行后，应得到 90 个结果、8 次 trap；先在 checks.txt 搜索 ADDI_NEGATIVE，确认期望为 0x0000000d，再跑 make sim。若 FAIL result[N]，用 checks.txt 的第 N 项反查测试名、实际寄存器和期望值。不能只把 expected 改成 DUT 当前输出以绕过失败，期望应按指令语义独立计算。

## 修改独立模块测试数据

每个 bench 位于 model_tb/unit/tb_<模块>.sv。修改输入 stimulus、期望值和 $fatal 条件，然后运行对应的单项测试。例如编辑 tb_lsu.sv 后运行：

~~~powershell
make unit-lsu
make regression-check
~~~

增加一个行为检查时，保持 DUT 信号稳定后等待组合逻辑传播（#1）或时钟沿，再比较预期值。失败用 $fatal(1, "清楚说明失败点")，不要仅用 $display("FAIL") 后正常 $finish，否则仿真器可能返回成功。通过路径输出唯一的 PASS tb_<module> N checks，回归器依赖该完成标记判定通过。

例如在 tb_alu.sv 的 initial 内、输出 PASS 之前增加：

~~~systemverilog
check(`ALU_ADD, 32'd20, 32'd22, 32'd42);
~~~

check 的四个参数分别是运算码、操作数 a、操作数 b、独立期望值。它会自动等待 #1、比较输出并增加检查计数；无需 make program，直接 make unit-alu 即可。这个例子会把 ALU 从 10 项增加到 11 项。对于时序模块，在下降沿设置输入、下一上升沿后 #1 检查输出，避免与 DUT 的非阻塞赋值竞争。

tb_rv32_core.sv 与 tb_top_module.sv 通过 core_test_env.vh 共享程序构造函数、内存和 scoreboard，但分别实例化自己的 DUT。改共享程序时要同时验证二者；bench 期望的 trap PC/cause/mtval 也要与程序中的真实编码对应。

## 修改流程建议

1. 编辑生成器或对应 bench 源文件。
2. 运行一个对应的单项测试，先快速定位问题。
3. 若更改整核生成程序，运行 make program 更新派生镜像。
4. 运行 make regression-check 做完整验证。
5. 检查源码和生成文件 diff，再一并提交。
